# `/New-Brain` Meta-Skill — Design Spec

**Date:** 2026-05-24
**Owner:** Roi Weiss (Product, MyHeritage)
**Status:** Approved for implementation planning
**Pilot scope:** v1 ships the meta-skill and uses it to bootstrap a second real brain (Backoffice or Site). v2 (shared catalog) is deferred.
**Predecessor:** `~/Claude/docs/superpowers/specs/2026-05-24-product-brain-design.md` (the original Product Brain design that the Billing pilot implements).

---

## 1. Purpose

Let any PM at MyHeritage build a high-quality domain brain — same shape, same workflow, same quality bar as the Billing pilot — in a single Claude Code session.

The artifact is a Claude Code meta-skill, `/New-Brain`, distributed as its own self-contained git repo (`mh-new-brain`) following the exact pattern of the existing `mh-billing-brain` repo.

**Why a meta-skill, not an HTML wizard or CLI:** the brain lives in Claude Code; the per-topic interview lives in Claude Code; query/capture/refresh all live in Claude Code. A meta-skill keeps the PM in one conversational surface from day-zero onward, applies the "interview-driven, not doc-dump" principle of the original design spec one level up (to the bootstrap itself), and produces a brain that already has identity, stakeholders, anchor references, and one real topic interview before the adoption cliff.

## 2. v1 / v2 split

**v1 — this spec:**

- `/New-Brain` Claude Code meta-skill exists, installs the same way `/Billing-Brain` does.
- Bootstraps a self-contained `mh-<domain>-brain/` repo locally per invocation.
- Bootstrap is a full guided start: identity → stakeholders/anchor docs → topic collection (hybrid doc + conversation) → scaffold → optional first-topic interview handoff.
- Produces brains structurally identical to `mh-billing-brain`.
- Leaves brain repos git-initialized locally but does NOT push to any remote.

**v2 — deferred, designed-for:**

- Shared catalog / discovery UI: any PM can browse and consult any other PM's brain.
- One-click install of someone else's brain.
- Cross-brain query / umbrella skill.
- Live ingestion from Confluence / Jira during bootstrap.
- Auto-push to a shared internal git org.

v1 leaves the metadata and structural conventions in place so v2 can be added without rework. v1 does not commit to any specific v2 mechanism (Anthropic plugin marketplace vs internal git org vs custom catalog) — the decision is deferred until 2-3 brains exist.

## 3. Architecture

Two artifacts in v1, both following the existing `mh-billing-brain` pattern:

### A. The meta-skill repo: `mh-new-brain/`

```
mh-new-brain/
├── README.md                  ← install + usage
├── SKILL.md                   ← /New-Brain skill definition
├── install.sh                 ← deploys SKILL.md → ~/.claude/skills/New-Brain/
├── scripts/
│   └── sync-templates.sh      ← regenerates templates from mh-billing-brain (see §7)
├── templates/                 ← canonical files copied into each new brain
│   ├── SKILL.md.tmpl
│   ├── README.md.tmpl
│   ├── install.sh.tmpl
│   ├── .gitignore
│   └── brain/
│       ├── brain.md.tmpl
│       ├── _meta.md.tmpl
│       ├── interview-log.md.tmpl
│       └── references/        ← empty, .gitkeep
└── docs/
    └── design-spec.md         ← this document
```

The `templates/` folder is the single source of truth for the per-brain shape. Bootstrapping a domain means: copy templates → substitute placeholders → write to the new repo. No string-mangling logic scattered across the skill body.

### B. The per-brain repo: `mh-<domain>-brain/` (one per PM-domain, generated by `/New-Brain`)

Identical structure to `mh-billing-brain`:

```
mh-<domain>-brain/
├── README.md
├── SKILL.md                   ← /<Domain>-Brain skill (templated copy of Billing's)
├── install.sh                 ← deploys to ~/.claude/skills/<Domain>-Brain/ + ~/Claude/brains/<domain>/
├── brain/
│   ├── brain.md
│   ├── _meta.md               ← seeded with domain identity + topic table
│   ├── interview-log.md       ← contains the bootstrap conversation as its first entry
│   └── references/            ← stubs for anchor docs the PM named
└── docs/
    └── design-spec.md         ← copy of the original Product Brain design spec
```

### Why two artifacts, not one

The meta-skill (`/New-Brain`) and the per-domain skill (`/<Domain>-Brain`) have completely different jobs and lifecycles. Bundling them would force every brain repo to re-ship the bootstrap code. Keeping them separate means the meta-skill can evolve independently, and each brain stays slim and focused on its runtime.

### The first-interview handoff

When `/New-Brain` finishes scaffolding, the new `/<Domain>-Brain` skill becomes available immediately (the bundled `install.sh` is run as the last bootstrap step). `/New-Brain` ends with: *"Your brain is live. Want me to start your first topic interview now?"* If yes, the PM invokes `/<Domain>-Brain interview <topic>` in their next message and the new skill takes over with the same interview workflow that runs Billing today.

## 4. The bootstrap conversation (five phases)

Each phase has a clear exit condition; the skill does not move on until the previous one is captured. All answers are written to `brain/interview-log.md` as they happen, not at the end.

### Phase 0 — Pre-flight (silent, before Phase 1)

1. **In-progress bootstrap?** Scans `~/Claude/mh-*-brain/brain/interview-log.md` files for a `## Bootstrap` entry without a corresponding `## Bootstrap complete` marker. If found, prompts: *"You have an unfinished `<DOMAIN>` bootstrap. Resume, restart, or discard?"*
2. **Write permissions.** Verifies write access to `~/Claude/`, `~/Claude/brains/`, `~/.claude/skills/`. If denied, surfaces the exact path + suggests `chmod` / sudo path rather than failing mid-scaffold.

### Phase 1 — Domain identity (≈2 min)

Prompts, one at a time:

- *"What's the domain called?"* (e.g. Billing, Backoffice, Site, DNA, Family Tree) → captures `domain-name`. Derives `slug` (kebab-case) and `skill-name` (`<Domain>-Brain`). Confirms back.
- *"In one paragraph, how would you describe this domain to someone joining MyHeritage tomorrow?"* → captures `description`.
- *"Who's the audience for this brain? (just you / your band / cross-functional PMs / the whole product org)"* → captures `audience`.

**Conflict check at end of Phase 1:** if `~/Claude/mh-<domain>-brain/`, `~/Claude/brains/<domain>/`, or `~/.claude/skills/<Domain>-Brain/` already exist, prompts: *"A `<DOMAIN>` brain already exists. Options: (a) pick a different name, (b) cancel, (c) overwrite with backup."* Default action is cancel; never silently overwrites.

### Phase 2 — Stakeholders and anchor docs (≈2 min)

- *"Who are the key people I should know about for this domain? Names + roles, briefly."* → captures stakeholder list.
- *"What are the 1-3 documents you'd hand a new hire as 'read these first'? Confluence URLs, PRDs, dashboards, contracts — whatever's gospel."* → captures anchor docs. For each, creates a stub in `references/` with `status: missing` (or `status: linked` if a URL was given).

If stakeholder content is substantive, a `Band & Team` topic is pre-written in `brain.md` with status `interviewed` and the stakeholder list as Facts — mirroring how Roi's Billing brain currently looks.

### Phase 3 — Topic collection (≈3-10 min, hybrid path)

Fork:

- *"Do you have an onboarding doc, Confluence page, CSV, or any source that lists the topics in your domain? Paste it, share a URL, or tell me there isn't one."*

**If a source is provided:** skill extracts a draft topic table (topic name + 1-line summary per row), shows it back, asks: *"Here's what I pulled. Edit, add, remove — tell me what to change."* Loops until the PM says "looks good."

**If no source:** skill runs three conversational probes:

1. *"What categories does your day-to-day work split into? Big buckets, not details."*
2. *"What would a new PM need to know that isn't obvious from reading the codebase or PRDs?"*
3. *"What does the broader org get wrong about your domain?"*

Generates a draft table from the answers; same review loop.

**Doc parsing fallback:** if the pasted content can't be cleanly extracted (malformed, too large, unreadable), skill falls back to the conversation-only path with: *"I couldn't get a clean topic list from what you pasted. Let's do this conversationally instead — same outcome, slightly slower."* The pasted content is still saved verbatim to `interview-log.md`.

Exit condition: PM confirms the topic list. Result: a topic table with N rows, each row having `name`, `one-line-summary`, `status: empty`.

### Phase 4 — Scaffolding (≈30 sec, automated)

1. Creates `~/Claude/mh-<domain>-brain/` directory.
2. Copies all templates from `mh-new-brain/templates/`, substituting placeholders (§5).
3. Writes `_meta.md` with domain identity + topic table.
4. Writes the bootstrap conversation verbatim into `brain/interview-log.md` as the first entry: `## Bootstrap — YYYY-MM-DD`.
5. Initializes the repo as git (`git init` + initial commit "Initial scaffold via /New-Brain"). Does NOT add a remote or push.
6. Runs the new repo's `install.sh` (with a `--dry-run` first to surface any backup actions and confirm). Deploys `SKILL.md` → `~/.claude/skills/<Domain>-Brain/` and `brain/` → `~/Claude/brains/<domain>/`.
7. Writes the completion marker `## Bootstrap complete — <date>` to `interview-log.md`.
8. Prints a confirmation block: paths created, skill activated, next-step command.

### Phase 5 — First topic handoff (optional, ≈5-15 min)

- *"Your brain is live. Want to do your first topic interview now? I'd suggest starting with `<topic>` — it's the one you were most animated about in Phase 2 / 3."*
- **If yes:** PM is instructed to invoke `/<Domain>-Brain interview <topic>` in their next message. `/New-Brain`'s job is done; the new per-domain skill takes over with the same interview workflow that runs Billing today.
- **If no:** `/New-Brain` exits, leaves a one-liner about how to start later.

## 5. Output contents (what gets written)

### Placeholders

| Token | Example | Source |
|---|---|---|
| `<DOMAIN>` | `Backoffice` | Phase 1 |
| `<domain-slug>` | `backoffice` | derived (kebab-case) |
| `<Skill-Name>` | `Backoffice-Brain` | derived (`<DOMAIN>-Brain`) |
| `<skill-cmd>` | `/Backoffice-Brain` | derived |
| `<description>` | one-paragraph blurb | Phase 1 |
| `<audience>` | `Backoffice PMs + Support liaisons` | Phase 1 |
| `<owner>` | `Roi Weiss` | Claude Code user identity / git config |
| `<bootstrap-date>` | `2026-05-24` | today |

### Per-file shape after substitution

- **`SKILL.md`** — clone of `mh-billing-brain/SKILL.md` with every `Billing-Brain` → `<Skill-Name>`, every `~/Claude/brains/billing/` → `~/Claude/brains/<domain-slug>/`, and the description line replaced with `<description>`. Command logic (query / interview / verify / status / capture / refresh) and hard rules stay identical — these are domain-agnostic. The current `SKILL.md` is the canonical source; it gets re-templated whenever it changes via the sync script.

- **`brain/_meta.md`** — seeded from bootstrap answers:

  ```markdown
  # <DOMAIN> Brain — Meta Index

  **Domain:** <DOMAIN>
  **Description:** <description>
  **Audience:** <audience>
  **Owner:** <owner>
  **Bootstrapped:** <bootstrap-date>
  **Brain file:** brain.md
  **References folder:** references/

  ## Topic Index
  | # | Topic | Status | Last-updated | Refs | Summary |
  |---|-------|--------|--------------|------|---------|
  | 1 | <topic name> | empty | — | 0 | <one-liner from Phase 3> |
  | … | … | … | … | … | … |

  ## Status legend
  …

  ## Reference stub backlog
  - references/<anchor-doc-slug>.md — requested by Bootstrap on <bootstrap-date>
  ```

- **`brain/brain.md`** — header + the topic template comment block (identical to Billing's). Topic sections are NOT pre-created as empty H2 blocks; they stay implicit in `_meta.md` until the PM actually interviews each one. Exception: if Phase 2 stakeholder capture was substantive, a `Band & Team` topic block is pre-written with status `interviewed` and the stakeholder list as Facts — exactly mirroring how Roi's Billing brain currently looks.

- **`brain/interview-log.md`** — header + the bootstrap conversation transcript as the first dated entry, ending with the `## Bootstrap complete` marker once Phase 4 succeeds.

- **`brain/references/`** — one stub `.md` file per anchor doc named in Phase 2, plus `.gitkeep`.

- **`install.sh`** — copy of `mh-billing-brain/install.sh` with the two paths swapped (`SKILL_DST_DIR` and `BRAIN_DST`). Extended with a `--dry-run` flag that prints the actions it would take without performing them; used by `/New-Brain` in Phase 4 step 6.

- **`README.md`** — copy of the Billing repo's README with domain-specific substitutions and a snapshot section auto-generated from `_meta.md`.

- **`docs/design-spec.md`** — copy of the original Product Brain design spec (`~/Claude/docs/superpowers/specs/2026-05-24-product-brain-design.md`), unmodified, so each brain repo is self-documenting.

- **`.gitignore`** — identical to Billing's.

### Concrete example

`_meta.md` immediately after a Backoffice bootstrap: domain header block + topic table with 8 empty rows (the topics named by the PM) + status section + 2-entry reference stub backlog (the two Confluence pages the PM named in Phase 2). Total file: ~40 lines.

## 6. Distribution (how PMs get `/New-Brain` itself)

`/New-Brain` ships exactly the same way `/Billing-Brain` already ships — its own self-contained repo + install script:

```bash
git clone <mh-new-brain-repo-url> mh-new-brain
cd mh-new-brain
./install.sh
```

`install.sh` deploys `SKILL.md` → `~/.claude/skills/New-Brain/SKILL.md`. Default mode is `copy`; `--symlink` flag for maintainers — identical pattern to the Billing install script.

**Where the repo lives:** v1 assumption is an internal MyHeritage git host (GitHub Enterprise or equivalent). Discoverability is the same as any other internal tool — Slack, README, or the eventual v2 catalog. v1 does not depend on Anthropic's plugin marketplace.

**Updating:** PMs `git pull && ./install.sh`. No auto-update.

**Bootstrapping the bootstrapper (chicken-and-egg):** Roi builds and installs `mh-new-brain` first, validates it by using it to bootstrap a real second brain (Backoffice or Site — see §9), then shares the repo URL with the PM org. PMs onboard one at a time via the install script.

**Why not a single-command curl installer:** the two-step (clone + install) leaves the source repo on the PM's machine — needed for re-running `install.sh` after updates and for maintainer contributions back. Same reasoning as the Billing install.

## 7. Compatibility with the existing Billing brain

The Billing brain is *the* canonical example. `/New-Brain` must not require it to change, and must produce new brains that are indistinguishable from Billing structurally.

### Invariants

- `mh-billing-brain/` repo content — no migrations, no renames, no schema bumps.
- The deployed Billing skill at `~/.claude/skills/Billing-Brain/`.
- The live Billing brain at `~/Claude/brains/billing/`.
- The existing design spec at `~/Claude/docs/superpowers/specs/2026-05-24-product-brain-design.md` (referenced, not modified).

### How consistency is enforced

- `mh-new-brain/templates/SKILL.md.tmpl` is generated from `mh-billing-brain/SKILL.md` by mechanical substitution (every `Billing-Brain` → `<Skill-Name>`, every `~/Claude/brains/billing/` → `~/Claude/brains/<domain-slug>/`, description swap). It is NOT hand-edited.
- `mh-new-brain/scripts/sync-templates.sh` regenerates the templates from the live Billing files. Output is checked in. If Billing's `SKILL.md` evolves, templates are re-synced and committed deliberately.
- `templates/install.sh.tmpl` is similarly generated from `mh-billing-brain/install.sh` with the two path variables swapped.
- `templates/brain/_meta.md.tmpl`, `brain.md.tmpl`, `interview-log.md.tmpl`, `.gitignore` are derived from Billing's current versions.
- `README.md.tmpl` is derived from Billing's README with the domain-specific lines parameterized.

### The "Billing as reference" invariant

If you run `/New-Brain` to produce a hypothetical `mh-foo-brain/`, then diff it against `mh-billing-brain/`, the only differences should be (a) the substituted placeholder values and (b) the actual brain content (Billing has 1 interviewed topic; foo has 0). Structural shape is identical. A regression check (script or test) can assert this.

### No runtime coupling

`mh-new-brain` and `mh-billing-brain` are independent. Updating one does not require updating the other. `/Billing-Brain` continues to work whether or not `/New-Brain` is installed.

### v2 implication

Because every brain produced by `/New-Brain` has identical structure, a future catalog or cross-brain query layer can rely on shape conventions (e.g., "every brain has `_meta.md` with a topic table"). No per-brain schema discovery needed.

## 8. Error handling & resumability

### Pre-flight check (Phase 0)

See §4. Runs silently; reports any blocker before asking the first Phase 1 question.

### Mid-flow interruption (the resumability story)

Bootstrap answers are written to `brain/interview-log.md` *as they happen*. Format includes phase markers:

```markdown
## Bootstrap — 2026-05-24
### Phase 1: Identity
Q: What's the domain called?
A: Backoffice
…
### Phase 2: Stakeholders & anchor docs
…
```

The completion marker `## Bootstrap complete — <date>` is written ONLY after Phase 4 step 6 (install.sh) succeeds. Anything short of that = unfinished = resumable.

If the session dies, the next `/New-Brain` invocation:

1. Detects the unfinished log via Phase 0.
2. Reads the last completed phase marker.
3. Says: *"Last time we got through Phase 2. Want to pick up at Phase 3, restart from scratch, or discard and start over?"*

### Conflict resolution for existing domain

If the PM types a name whose paths already exist:

- **All paths exist** (repo dir, brain dir, skill installed): *"A `<DOMAIN>` brain already exists at `~/Claude/mh-<domain>-brain/`. Options: (a) pick a different name, (b) cancel, (c) overwrite with backup (I'll move the existing repo to `mh-<domain>-brain.bak.<timestamp>` first)."* Default: cancel.
- **Partial state** (only some paths exist): same three options, flagged explicitly.

### Input validation

- **Domain name:** stripped of leading/trailing whitespace; rejected if empty, contains path separators (`/`, `\`), contains shell metacharacters, or doesn't start with a letter. PM sees the rejection reason and a sanitized suggestion.
- **Stakeholder list / topic list:** no validation; freeform text. Empty is allowed (solo-PM domain).
- **Anchor doc URLs/paths:** not validated for reachability in v1. Stubs are created either way with `status: missing` or `status: linked`.

### `install.sh` failure modes

- `/New-Brain` runs `install.sh --dry-run` first to surface backup actions and confirm with the PM before the real run.
- The script's built-in backup logic (from the Billing version) handles existing target files.
- If the real run fails, the partial repo at `~/Claude/mh-<domain>-brain/` is left in place for inspection — no automatic cleanup, no orphan skill at `~/.claude/skills/`.

### Doc parsing failures (Phase 3)

See §4 Phase 3 fallback.

### Explicitly NOT in v1 error handling

- Automatic recovery from `install.sh` failure (PM inspects manually).
- Automatic git remote configuration.
- Automatic doc-fetching from internal Confluence/URL during bootstrap (PM pastes content; live fetching is deferred — see §10).

## 9. Success criteria for v1

v1 is complete when **all** of the following hold:

1. **`/New-Brain` is installed via the same pattern as `/Billing-Brain`** — `mh-new-brain` repo exists, `./install.sh` deploys it cleanly, restarting Claude Code makes the skill available.
2. **A real second brain has been bootstrapped end-to-end using `/New-Brain`** — Backoffice or Site, Roi's choice. The resulting `mh-<domain>-brain/` repo passes the "Billing as reference" structural invariant from §7 (identical shape, only placeholder values differ).
3. **The bootstrapped brain has at least one topic at `interviewed` status** — proves Phase 5 (first-topic handoff) actually produces content.
4. **`/<New-Domain>-Brain status` produces a useful audit immediately after bootstrap** — new skill fully functional, with topic table, owner/description metadata, and reference stub backlog populated.
5. **Resumability has been exercised at least once** — bootstrap was interrupted (real or simulated) and `/New-Brain` resumed from the right phase without data loss.
6. **`mh-billing-brain` is unchanged** — `git status` on the Billing repo shows no diff caused by `/New-Brain`'s installation or use.
7. **The bootstrap conversation appears in the new brain's `interview-log.md`** — bootstrap is auditable; another PM (or future-Roi) can read how the brain was seeded.
8. **One other PM (or Roi acting as proxy) has successfully cloned `mh-new-brain` and run `/New-Brain` on a fresh machine** — proves the distribution path works, not just the local-author flow.

If all eight hold, `/New-Brain` is ready for broader PM-org rollout, and v2 (shared catalog) becomes the next planning conversation.

## 10. Out of scope (deferred to v2 or later)

Deliberately not building in v1:

- **Cross-brain / umbrella query** — no `/MH-Brain` that queries across installed brains. Revisit once 3+ brains exist.
- **Shared catalog / discovery UI** — the v2 sharing vision (browse all brains, one-click install, see who owns what). v1 leaves metadata for it.
- **Auto-push to a shared git org** — `/New-Brain` initializes the repo locally and commits, but does NOT add a remote or push. A future `/New-Brain publish` can wrap this.
- **Live ingestion from Confluence / Jira / Mixpanel** — the MCPs are available, but v1 requires the PM to paste content. Live fetching is a quality risk (stale/auth/parsing edge cases).
- **Bootstrap from existing PRD/spec dumps** — same reasoning. Paste-or-conversation only.
- **Topic AI-suggestion across PMs** — no "PMs in similar domains used these topics" recommendations.
- **Schema versioning / migration tooling** — brain shape is whatever `mh-billing-brain` looks like today. If it evolves, that's a deliberate manual update across templates + existing brains.
- **Brain merge / split** — no flow to absorb a sub-domain into a parent brain. Manual file moves only.
- **Permissions / access controls per brain** — every brain is fully readable by anyone who has it. Sharing happens at the repo-visibility level.
- **Non-PM domains** — v1 is scoped to MyHeritage *Product* domains. Engineering, ops, support knowledge bases can adopt the pattern later.
- **Web / HTML UI for `/New-Brain`** — meta-skill is Claude Code-native. HTML alternative is reconsidered only if a real non-CC PM audience emerges.
- **Analytics on brain usage** — no telemetry. If wanted later, it lives in the v2 catalog layer.
- **Multi-language support** — English-only for v1.

**Out-of-scope items explicitly preserved as v2 hooks:** the `_meta.md` metadata (domain, owner, description, audience, bootstrap-date) is rich enough that any future catalog can index brains without re-asking the PM. Repos are git-initialized so `git remote add origin && git push` is one command away.
