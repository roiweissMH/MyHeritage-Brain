02 · 18
The problem

Product knowledge is the most valuable asset on the team — and the worst documented.

PRDs go stale the day they ship. Slack threads vanish. The "why" behind half our decisions lives in the heads of two or three veterans.

Drift

Docs lie quietly.

A PRD was correct in 2024. Nobody told it about the changes shipped in 2025. New PMs trust the file; the file is wrong.

Tacit

The "why" is unwritten.

"Germany has a special termination flow." Why? "Legal said so in 2022." That sentence rarely makes it into any doc.

Onboarding

Three months to get up to speed.

Every new PM repeats the same conversations with the same veterans, extracting the same context. There is no compounding.

03 · 18
The idea

Treat each domain like onboarding a new hire — forever.

Instead of extracting knowledge from stale documents, we capture it the way you'd explain it to someone over coffee. Claude conducts a structured interview. The result is a markdown file you can read, edit, share, and query.

Interview-driven, not doc-dump. The PM is the source of truth for tacit knowledge. Existing docs are anchored as references, not treated as gospel. The brain captures both.
Old way

Extract from documents.

Read every PRD, every dashboard, every Slack export. Hope the documentation matches reality. Usually it doesn't.

New way

Interview the human.

Claude asks structured questions. You answer in your own words. The output is curated narrative grounded in what you actually know — citing references where they help.

04 · 18
The artifact

A brain is two things, together.

1 — A markdown knowledge base

One curated file per domain. Topic by topic: a plain-prose narrative, the key facts, the history & decisions, the open questions, and links to reference documents.

You can open it in any editor. You can read it on a train. It's not a database. It's a living document.

2 — A Claude Code skill

One slash command per domain — like /Billing-Brain or /DNA-Brain — that reads your brain and answers questions grounded only in what's there. No hallucination. Every answer cites its source.

Six commands: query, interview, verify, status, capture, refresh.

~/Claude/brains/<your-domain>/ ├── brain.md ← the knowledge artifact (narrative + facts per topic) ├── _meta.md ← topic index (status, last-updated, references) ├── interview-log.md ← raw transcripts (audit trail) └── references/ ← linked source docs (PRDs, pricing grids, etc.)

The tool

Type /New-Brain. Answer questions. Done.

One Claude Code command kicks off a guided 5-phase interview. You answer in your own words. Claude scaffolds the files, installs the new skill, and (optionally) walks you through your first real topic — all in one continuous session.

Phase 1

Identity

Name, description, audience, owner. ~2 min.

Phase 2

Stakeholders & docs

Key people. Anchor docs. ~2 min.

Phase 3

Topic collection

Paste a doc, or talk it through. ~3–10 min.

Phase 4

Scaffolding

Automated. Repo, skill, install. ~30 sec.

Phase 5

First topic

Optional. You leave with one topic done. ~5–15 min.

Phase 0

Pre-flight

Silent. Checks for unfinished sessions. Always safe to retry.

Phase 1 · ~2 minutes

Identity.

Claude asks four questions, one at a time. Each answer is confirmed back to you before moving on. No surprises.

Claude: What's the domain called? Examples: Billing, Backoffice, Site, DNA, Family Tree.
You:     Backoffice
Claude: Got it — Backoffice. The brain will live at ~/Claude/mh-backoffice-brain/,
        and you'll use /Backoffice-Brain in Claude Code. Sound right?
You:     Yes
Claude: In one paragraph, how would you describe this domain to someone joining
        MyHeritage tomorrow?
You:     The internal tools used by Support, Sales, and Ops to manage user
        accounts — refunds, comp orders, manual subscription edits, fraud
        review, and DNA shipment tracking.
Claude: Who's the audience for this brain? (just you / your band / cross-functional PMs / the whole product org)
You:     Backoffice PMs + Support liaisons
Claude: Owner of this brain will be recorded as Roi Weiss (from git config). Confirm or override?
You:     Confirm
09 · 18
Phase 2 · ~2 minutes

Stakeholders & anchor docs.

Two questions that surface the people and the documents your domain leans on. If you name docs you don't have on hand, Claude creates stubs and tracks them in a backlog you can fill in later.

Claude: Who are the key people I should know about for this domain? Names + roles, briefly.
You:     Tomer (PM), Yael (BE lead), Itamar (FE), Avivit (QA), Yossi (Support liaison)

Claude: What are the 1–3 documents you'd hand a new hire as "read these first"?
        Confluence URLs, PRDs, dashboards, contracts — whatever's gospel.
        Title + URL per line. Leave URL blank if it's just a known doc name.
You:     Backoffice onboarding guide | https://confluence.../backoffice-onboarding
        Refund policy v3 |
        Account merge runbook | https://confluence.../account-merge

The 3 anchor docs become stubs in your references/ folder. Two have URLs; one is tracked as "missing" in the backlog so you remember to attach it later.

10 · 18
Phase 3 · ~3–10 minutes

Topic collection — hybrid.

Two paths, your choice. If you already have an onboarding doc or topic list, paste it. Claude pulls topics out and you edit. If you don't, Claude asks three conversational probes and proposes a draft.

Path A You have a source

Paste an onboarding doc, a Confluence export, or a CSV. Claude extracts a draft topic table. You edit it. Loop until you say "looks good."

Path B No source

Claude asks three probes:

  • What categories does your day-to-day work split into?
  • What does a new PM need to know that isn't obvious from PRDs?
  • What does the broader org get wrong about your domain?

Same outcome — a draft topic table you can edit.

You always have final say. The topic table is reviewed and edited by you before scaffolding. Claude proposes; you decide.
11 · 18
Phase 4 · ~30 seconds, automated

Scaffolding.

Nothing for you to do. Claude calls the deterministic scaffolder, which fills the templates with your answers and writes the new repo. Then it runs the new repo's install script, deploying your skill into Claude Code.

# What happens behind the scenes:
$ scaffold.sh --domain "Backoffice" --slug "backoffice" --skill-name "Backoffice-Brain" \
              --description "..." --audience "..." --owner "..." \
              --topics-file /tmp/topics.txt --anchors-file /tmp/anchors.txt --interview-log-file /tmp/log.md
Scaffold complete: /Users/you/Claude/mh-backoffice-brain

$ cd ~/Claude/mh-backoffice-brain && ./install.sh
Copied: ~/Claude/mh-backoffice-brain/SKILL.md → ~/.claude/skills/Backoffice-Brain/SKILL.md
Copied: ~/Claude/mh-backoffice-brain/brain → ~/Claude/brains/backoffice
Install complete. Restart Claude Code, then run: /Backoffice-Brain status

If your stakeholder list in Phase 2 was substantive (3+ people), Claude also writes a Band & Team topic block into brain.md as your first interviewed topic — you leave Phase 4 with one real topic already done.

12 · 18
Phase 5 · ~5–15 minutes · optional

Your first topic interview.

Claude offers to walk you through the first real topic interview right then. You can decline — your brain is already live and you can come back any time. But this is where the magic happens. Saying yes means you leave with a brain that's not just scaffolded, but already useful.

Probe pattern

Six question types

  • Wide opener: "Walk me through how X works."
  • Facts probe: "Who owns it? Key systems? Numbers?"
  • History probe: "What changed in the last 1–2 years?"
  • Unwritten rules: "What do new PMs get wrong?"
  • Reference collection: "Which docs back this up?"
  • Open questions: "What don't you know yet?"
Result

One topic, fully captured

Narrative in your voice. Key facts as bullets. History entries with dates. Reference stubs for docs you named. Open questions queued for future sessions.

Status: interviewed (or verified once cross-checked against a real reference doc).

13 · 18
After bootstrap

Six commands for daily use.

Once your brain is live, you use the same six commands as /Billing-Brain. They're designed so a brain isn't a one-time artifact — it grows and stays fresh as your domain evolves.

CommandWhat it does
/<Domain>-Brain <question> Ask anything. Answer is grounded only in what's in your brain + linked references, with citations and status tags.
/<Domain>-Brain interview <topic> Run the structured 6-probe interview on a topic. Distills into brain.md. Use to fill an empty topic or expand a thin one.
/<Domain>-Brain status One-screen audit: topic coverage, stale topics, oldest open questions, reference backlog, action suggestions.
/<Domain>-Brain capture <topic> "..." Quick in-the-moment append. A decision in standup? Capture it before it slips. Dated, in the history section, auto-marked unverified.
/<Domain>-Brain refresh <topic> Delta interview. "What's changed since the last-updated date?" Targeted, fast, designed for periodic upkeep.
/<Domain>-Brain verify <topic> Cross-check the brain's facts against attached reference docs. Promotes status to verified, or flags discrepancies as open questions.

A working example

What a real query looks like.

A real exchange with the Billing brain. Notice how the answer cites its source, tags its confidence, and surfaces open questions.

You:     /Billing-Brain who do I talk to about a chargeback dispute?

/Billing-Brain:
        For chargeback disputes, the operational owner is Chanan (Billing operations).
        (Topic: Band & Team, Facts, status: interviewed)

        For day-to-day routing and fraud rule decisions affecting chargebacks, the
        Payments and Risk Expert role is who owns the external-vendor relationships
        (Adyen, Stripe, Bluesnap). That role is part of the Billing band's standard
        composition. (Topic: Band & Team, Narrative, status: interviewed)

        For escalation or company-level questions, route to Roi Weiss (Billing
        domain expert, ~8 years leading the band).
        (Topic: Band & Team, Facts, status: interviewed)

        References used:
        - references/billing-band-composition.md

        Open questions on the topics touched:
        - Head count and role assignments should be refreshed periodically — who
          currently holds which role?

No fabrication. No "Billing best practices" boilerplate from the internet. Just what your brain knows — with provenance.

Setup

Install in 3 lines.

If you already have Claude Code installed and configured, getting /New-Brain running on your machine is a one-time, three-line setup.

$ git clone <internal-git-url>/mh-new-brain ~/Claude/mh-new-brain
$ cd ~/Claude/mh-new-brain && ./install.sh
Copied: ~/Claude/mh-new-brain/SKILL.md → ~/.claude/skills/New-Brain/SKILL.md
Install complete. Restart Claude Code, then run: /New-Brain
$ # Restart Claude Code. /New-Brain is now available.

Don't have Claude Code yet?

You'll need it to use any brain (yours or someone else's). Setup docs and access provisioning: ping Roi or the PM tooling channel.

Updates later

$ cd ~/Claude/mh-new-brain && git pull && ./install.sh

That's it. No auto-update mechanism, no version negotiation. You pull when you want changes.

Sharing

How brains travel.

Every brain is a self-contained Git repo. Sharing one is as boring as pushing a repo — which is exactly the point.

/New-Brain itself

Lives in one shared repo

The bootstrapper lives at mh-new-brain on MyHeritage's internal Git. Each PM clones it once, runs ./install.sh, and has /New-Brain available forever (until they delete it).

Your own brain

Also a Git repo — yours to share

The repo Claude scaffolds for you (mh-<domain>-brain) is git-initialized locally with no remote. When you're ready to share with the team, push it to internal Git. Other PMs can then clone it and run its install.sh to consult your brain alongside their own.

Pushing your brain when you're ready

$ cd ~/Claude/mh-<your-domain>-brain
$ git remote add origin git@<internal-git>:mh-<your-domain>-brain.git
$ git push -u origin main
v2 vision. Once 2–3 domain brains exist as shared repos, we build a small catalog so any PM can browse "what brains are available" and one-click install the ones relevant to their work. The metadata in _meta.md already supports it. We're not building the catalog yet — but every brain shipped today is forward-compatible.
